# Локализация: переезд на ARB — что сделано и почему

Отвечает на пункт аудита 4.3. Дата: 16 сентября 2026.

## Коротко

- Источник правды теперь — `lib/l10n/app_en.arb` + `lib/l10n/app_ru.arb` (1468 записей: 1443 обычные строки, 24 переиспользуемые ICU-плюральные семьи, 1 составное предложение).
- Подключена официальная схема Flutter: `l10n.yaml`, `flutter_localizations` в `pubspec.yaml`, `generate: true`. При `flutter pub get` генерируется настоящий `AppLocalizations` класс — им стоит пользоваться в новом коде: `AppLocalizations.of(context).xyz`.
- Все ~1800 существующих вызовов `'строка'.tr` продолжают работать **без единой правки call site** — `app_translations.dart` теперь не хранится руками, а **генерируется** из ARB (`tools/l10n/generate_compat_layer.py`).
- Реальные ICU-плюралы: 58 мест с `ruCount(...)`/`ruPluralForm(...)` (полным списком явных `one:`/`few:`/`many:` на каждом вызове) свёрнуты в 24 семьи + 1 составное сообщение, вызовы переписаны на короткие `nCount('key', n)` / `nOnly('key', n)`.
- Новый статический чекер `tools/l10n/check_missing_translations.py`: сканирует **все** `.tr`-вызовы в проекте и сверяет с ARB. Сейчас: **0 пропусков на 1694 местах**. Это и есть настоящий ответ на «поменял текст — перевод тихо отвалился»: раньше это можно было заметить только глазами на устройстве, теперь — одна команда, которую можно повесить на CI.

## Почему не просто «переехали на `AppLocalizations.of(context)` везде»

Официальный сгенерированный класс требует `BuildContext`. Огромная часть из 1800 вызовов `.tr` сидит не в `build()`, а в статических хелперах, форматтерах моделей, функциях без виджета вообще — контекста там физически нет. Переписать всё это разом — не рефакторинг локализации, а отдельный, гораздо более рискованный архитектурный рефакторинг, который нельзя грамотно проверить без живого dart-компилятора (которого в этой среде нет).

Поэтому выбор был такой: ARB — единственный источник правды и для нового `AppLocalizations`, и для старого `.tr`. Новый код — через `AppLocalizations.of(context)` (типизировано, автодополнение, проверка на этапе сборки). Весь существующий код — как был.

## Файлы

| Файл | Роль |
|---|---|
| `lib/l10n/app_en.arb`, `app_ru.arb` | Источник правды. Редактировать вручную, потом прогонять `generate_compat_layer.py`. |
| `l10n.yaml` | Конфиг для `flutter gen-l10n` (официальный генератор Flutter). |
| `lib/l10n/app_localizations.dart` | **Не в архиве** — генерируется автоматически при `flutter pub get` (стандартное поведение `generate: true`, как в любом Flutter-проекте с ARB; такие файлы принято не коммитить). |
| `lib/services/app_translations.dart` | **Сгенерированный файл** — шапка файла так и говорит. Не редактировать руками, перегенерировать через скрипт ниже. |
| `tools/l10n/generate_compat_layer.py` | ARB → `app_translations.dart`. Запускать после любой правки `.arb`. |
| `tools/l10n/check_missing_translations.py` | Статическая проверка покрытия. Годится для CI: `python3 tools/l10n/check_missing_translations.py --ci`. |
| `tools/l10n/build_arb.py` | Историческая справка — как именно были извлечены исходные 1452 пары из старых двух словарей. Не часть обычного цикла разработки. |

## Как добавить новую переводимую строку

1. В коде: `'новый текст'.tr` — как раньше, ничего не поменялось для существующего стиля работы.
2. В `lib/l10n/app_en.arb` и `app_ru.arb` добавить пару под тем же ключом (произвольным, но по конвенции — lowerCamelCase от английского текста).
3. `python3 tools/l10n/generate_compat_layer.py`.
4. Опционально: `python3 tools/l10n/check_missing_translations.py` — убедиться, что ничего не забыто.

Для нового кода вместо `.tr` лучше сразу `AppLocalizations.of(context).newTextKey` — после `flutter gen-l10n` это доступно из коробки, с автодополнением в IDE и проверкой при сборке (несовпадение плейсхолдеров между `en`/`ru` — ошибка сборки, а не баг в рантайме).

## Множественные числа

Раньше — либо `ruCount(n, one: 'день', few: 'дня', many: 'дней', englishOne: 'day', englishOther: 'days')` на каждом вызове (58 мест, полное дублирование форм), либо (что хуже) 3 самописные приватные функции `_dayWord`/`_evening`/`_point`, дублирующие одну и ту же формулу mod10/mod100 в разных файлах — из прошлой сессии, тоже переведены на общий механизм.

Теперь — 24 именованные семьи в `pluralCatalog` (`nDays`, `nEvenings`, `nTitles`, `nFriends`, …), заданные один раз через ARB ICU-синтаксис:
```json
"nDays": "{count, plural, one {{count} день} few {{count} дня} many {{count} дней} other {{count} дня}}"
```
Использование в коде — `nCount('nDays', 5)` → `"5 дней"`, `nOnly('nDays', 5)` → `"дней"` (когда число уже показано отдельно, например в дроби `3/5`).

Один особый случай — `friendsJoinedWithCode(count, xp)` в `invite_friends_sheet.dart`: целое предложение с согласованием и существительного, и глагола («N друзей присоединились…» / «N друг присоединился…»), поэтому не влезает в обычную схему «число + существительное» и вынесено отдельной функцией.

## Реально найденные и исправленные баги

При прогоне статического чекера по всему проекту нашлось всего 10 несостыковок на 1694 места — заметно меньше, чем можно было бы ожидать после аудита. Разобрано:

- **`sincerity_toast.dart`** — настоящий баг: `.tr` вызывался на уже интерполированной строке (`'+${award.delta} · ...'`。tr`), которая физически не может совпасть ни с одной статической записью словаря, потому что каждый раз разная. `.tr` просто молча ничего не делал. Исправлено — `.tr` теперь оборачивает только стабильную часть фразы, число подставляется вокруг уже переведённого текста.
- **`app_translations.dart`'s собственный генератор** — при первой версии скрипта неправильно вычислял границу plural-блока (`rindex('}')` вместо честного подсчёта глубины скобок), из-за чего суффикс `— +{xp} xp so far` вырезался вместе с самим `{xp}` — количество опыта просто пропадало бы из фразы. Поймано и исправлено до того, как попало в сгенерированный файл.
- **`'наш дневник'`** в настройках — забыл добавить перевод в прошлой сессии при добавлении совместного дневника. Добавлено.
- 5 строк в онбординге и профиле — были на английском без русского перевода вообще (`favorite_films_screen.dart`, два ярлыка выбора темы оформления, две мокап-подписи под дату в превью онбординга). Переведены с подбором тона по соседним уже переведённым фразам того же экрана.

## `wrapped_screen.dart` — уточнение к прошлому аудиту

В прошлом аудите этот файл (4084 строки) был назван «вообще не переведён». При детальной проверке в этой версии архива (по границам функций/классов, а не по окну в несколько строк) выяснилось, что это **не так** — файл уже почти полностью двуязычен, просто не через `.tr`, а через параллельные структуры: пары функций (`_periodPossessive`/`_periodPossessiveEn`), пары констант (`_labelRu`/`_labelEn`, `_monthNames`/`_monthNamesEn`) и инлайн-тернарники `LocaleService.appIsRussian ? ... : ...`. Из 59 вызовов `.tr` в этом файле — все 59 имеют покрытие в ARB. Единственная реальная правка здесь не понадобилась; экономия оказалась там, где её не ждали.

## Что осталось не сделано (честно)

- **`AppLocalizations.of(context)` не применён ни в одном call site** — вся инфраструктура готова и официально сгенерируется при `flutter pub get`, но перевод существующего кода на неё — отдельная, менее срочная задача, делать её стоит постепенно, файл за файлом, с живым компилятором под рукой.
- **Не запускался `flutter gen-l10n` / `flutter analyze`** — в этой среде нет Flutter SDK. Всё проверено на уровне: валидность JSON у ARB, баланс скобок у изменённых файлов, отсутствие висячих ссылок на удалённые функции, работоспособность генераторов на реальных данных. Первый `flutter pub get` в реальном окружении стоит сделать с вниманием к консоли — если генератор найдёт несоответствие плейсхолдеров между `app_en.arb` и `app_ru.arb`, он честно упадёт со сборкой, и это будет первая проверка, которую эта миграция ещё не проходила вживую.
- Слова "конкатенация вместо шаблонов целого предложения" — за пределами явных `ruCount`/`ruPluralForm`-мест этот паттерн мог остаться и в других местах приложения (не только в разобранном `invite_friends_sheet.dart`). Отдельный `check_missing_translations.py` его не ловит, потому что технически каждый фрагмент по отдельности переведён — просто порядок слов при сборке через `+`/интерполяцию может звучать неестественно на одном из языков. Обнаруживается только чтением экрана целиком на обоих языках.
