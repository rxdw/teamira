# Аналитика: как она устроена и как её смотреть

Коротко: приложение записывает, какие экраны открывают и какие ключевые действия делают, и отправляет это на ваш же бэкенд. События лежат в вашем Postgres (таблица `analytics_events`). Никаких сторонних сервисов, аккаунтов и ключей. Смотреть их можно тремя способами: командой-отчётом (ничего настраивать не надо), **графиками в Grafana** (готовый дашборд в проекте, настроить один раз) или в Metabase (кликаете сами).

## 1. Как это устроено

```
телефон                          ваш сервер
───────                          ──────────
экран открылся ─┐
действие        ├─► очередь ─► POST /analytics/events ─► таблица analytics_events (Postgres)
сворачивание    ┘   (пачками)                                   │
                                                  ┌─────────────┴──────────────┐
                                        scripts/analytics_report.py     Metabase (дашборды)
                                        «отчёт в терминале»             через read-only роль
```

- **Экраны пишутся сами.** `AnalyticsRouteObserver` (`mobile/lib/analytics/`) видит каждый открытый экран и шторку и называет их по имени класса (`TitleDetailScreen`). Ни в одном экране ничего дописывать не нужно. Вкладки (Дневник, Подборки, Профиль, Главная), логин, EULA, онбординг и приветствие объявляют себя явно.
- **Отправка пачками:** через 15 секунд после первого события, при накоплении 25 штук и при сворачивании приложения. Если сети нет, события ждут в очереди (она сохраняется на диск) и уходят позже.
- **Повторы безопасны:** у каждого события свой случайный id, сервер второй раз то же событие не запишет.
- **Кто это:** `anon_id` — случайная строка, одна на установку приложения. Если человек вошёл в аккаунт, сервер сам добавляет `user_id` из токена (клиент его не присылает и подделать не может).

## 2. Как смотреть в проде

### Способ А. Отчёт командой (начните с него)

```bash
# за последние 7 дней, все сборки (при разработке это ваши debug-запуски)
docker compose exec api python -m scripts.analytics_report

# когда появятся реальные пользователи: только релизные сборки, за месяц
docker compose exec api python -m scripts.analytics_report --days 30 --build release

# показать больше строк в таблицах
docker compose exec api python -m scripts.analytics_report --days 30 --top 100
```

На сервере то же самое, только сначала зайти по SSH (`ssh user@server`, перейти в папку проекта). Если хотите сохранить отчёт файлом: добавьте `> report.txt`.

Что в отчёте и как читать:

| Раздел | Что отвечает |
|---|---|
| **Кто пользуется** | Сколько устройств было активно сегодня / за 7 / за 30 дней, сколько новых, сколько вошли в аккаунт, средняя длина сессии. |
| **Экраны: что открывают** | Рейтинг экранов: сколько открытий, на скольких устройствах, какой процент активных до него дошёл, среднее время на экране. |
| **Экраны, которые не открыли НИ РАЗУ** | Ответ на вопрос «какими из ~60 экранов вообще не пользуются». Экраны из исходников минус открытые за период. |
| **Шторки** | То же для bottom sheet. |
| **Действия** | Сколько раз и сколькими устройствами сделаны ключевые действия (запись в дневник, поиск, вопрос Тамире…). Отдельной строкой: сколько поисков закончились без результатов. |
| **Онбординг: где отваливаются** | Сколько устройств дошло до каждого из 10 шагов и до конца. |
| **Путь до первой записи в дневник** | Открыли приложение → зарегистрировались → искали → открыли тайтл → записали вечер. |
| **Возвращаемость** | Какая доля новых устройств вернулась на 1-й и 7-й день. |
| **Платформы, версии, язык** | Из чего состоит аудитория. |

Читать с осторожностью:

- **Малая выборка.** Пока в приложении десятки устройств, проценты шумные. Отчёт сам предупреждает про удержание, когда данных мало. Смотрите на порядок величин, а не на десятые доли.
- **«Не открыли ни разу» ≠ «не нужен».** Экран может быть глубоко в настройках или нужен раз в год. Смотрите период побольше (`--days 90`) и решайте головой.
- **Считаются устройства, а не люди.** Два телефона у одного человека = 2, переустановка = ещё одно новое устройство.
- **Время на экране приблизительное:** это время до следующего перехода или до сворачивания, не больше 10 минут (иначе телефон, забытый на столе, «делает» экран самым популярным).

### Способ Б. Графики в Grafana (готовый дашборд, рекомендую для «красиво смотреть»)

Grafana — открытая программа для дашбордов. Она подключается прямо к вашему Postgres, ничего не хранит у себя, кроме настроек, и **уже настроена в проекте**: сервис в `docker-compose.yml`, подключение к базе и готовый дашборд «Seenly — использование приложения» лежат в папке `grafana/`. Кликать и писать запросы не нужно.

Что на дашборде (17 панелей):
- Сверху четыре числа: активные устройства, новые, сессии, вошедшие в аккаунт.
- Графики по дням: активные устройства и сессии; регистрации и записи в дневник (последние два считаются по таблицам приложения, а не по событиям, поэтому включают и тех, кто выключил статистику).
- Экраны: таблица-рейтинг (открытия, устройства, среднее время), топ-15 столбиками, отдельно шторки.
- Онбординг по шагам (где отваливаются), действия столбиками, открытия выбранных экранов и выбранных действий по дням.
- Доля поисков без результатов, возвращаемость по когортам (D1/D7), платформы и версии.
- Вверху три переключателя: **Сборка** (оставьте `release`, когда появятся реальные люди — так ваши debug-запуски не мешают), **Экран**, **Действие**; и период справа вверху.

**Настройка (один раз):**

1. **Роль только для чтения.** Grafana подключается не логином приложения, а ролью, которая видит только аналитику и **не видит** `users`, `diary_entries` и остальное. Новые вьюхи (`v_analytics_registrations_daily`, `v_analytics_diary_daily`, `v_analytics_premium_daily`, `v_analytics_retention`) отдают только даты, категории и счётчики. Создайте роль один раз (в dev-окружении; на проде — команда с именами вашего `postgres`-сервиса из плана, фаза 2.14.2):

```bash
docker compose exec db psql -U seenly -d seenly -c "
CREATE ROLE grafana_ro LOGIN PASSWORD 'ПРИДУМАЙТЕ-ДЛИННЫЙ-ПАРОЛЬ';
GRANT CONNECT ON DATABASE seenly TO grafana_ro;
GRANT USAGE ON SCHEMA public TO grafana_ro;
GRANT SELECT ON analytics_events, v_analytics_screen_views, v_analytics_daily_active, v_analytics_events_daily,
                v_analytics_registrations_daily, v_analytics_diary_daily, v_analytics_premium_daily, v_analytics_retention TO grafana_ro;"
```

2. **Пароли.** В файл `.env` рядом с `docker-compose.yml` (образец — `env.example`):
```
GRAFANA_ADMIN_PASSWORD=пароль-для-входа-в-Grafana
GRAFANA_DB_PASSWORD=тот-же-пароль-что-в-CREATE-ROLE
```
3. **Запуск:** `docker compose --profile analytics up -d grafana`
4. **Открыть:** http://localhost:3001, логин `admin`, пароль из `GRAFANA_ADMIN_PASSWORD`. Слева «Dashboards» → «Seenly — использование приложения».
5. **На сервере:** порт привязан только к `127.0.0.1`, наружу не торчит и не должен. С вашего компьютера: `ssh -L 3001:localhost:3001 user@server`, не закрывая окно, откройте http://localhost:3001.

**Если хотите смотреть на своём компьютере, а не через туннель к Grafana сервера:** запустите Grafana локально (тот же `docker-compose.yml`) и направьте её на базу сервера. Для этого на сервере опубликуйте Postgres **только на localhost** (`127.0.0.1:5432:5432` у сервиса с базой), с компьютера — `ssh -L 5432:localhost:5432 user@server`, и в `.env` локальной копии `GRAFANA_DB_HOST` должен указывать на туннель (на Windows/Mac из контейнера это `host.docker.internal:5432`). Проще и надёжнее всё же Grafana на сервере и один туннель.

**Как менять дашборд.** Он загружается из файла `grafana/dashboards/seenly-usage.json` и в интерфейсе заблокирован от сохранения (чтобы на сервере всегда было ровно то, что в git). Правьте в Grafana как обычно, затем «Share → Export → Export as JSON» и замените этим файлом `seenly-usage.json` в репозитории; через минуту Grafana подхватит. Хотите ещё одну панель — «Add → Visualization», источник уже выбран, запросы к вьюхам `v_analytics_*` и таблице `analytics_events` (для панелей на время используйте `$__timeFilter(ts)`, фильтр по сборке — `build IN ($build)`).

**Оповещения** (например «за час ни одного события» или «всплеск ошибок») в проекте не настроены. Grafana умеет их сама (Alerting → Alert rules) и присылать в Telegram/почту; это следующий шаг, когда будет что защищать.

**Что проверено, а что нет:**
- Проверено на настоящей Grafana 13.2.2 и Postgres 16: датасорс подключается ролью `grafana_ro` (Database Connection OK), дашборд загружается из файла, все 18 запросов панелей выполняются через Grafana с реальными данными. Роль читает вьюхи и не читает `users`, `diary_entries`, `user_premium_state`. Тесты на вьюхи есть в `backend/tests/test_analytics.py`.
- **Не проверено:** внешний вид (у меня не было браузера, панели я не видел глазами: если какая-то отображается криво, поправьте в интерфейсе и сохраните через Export), а также сам docker-сервис (образ `grafana/grafana-oss:latest`, в моём окружении нет Docker). Перед выкладкой на сервер замените `latest` на конкретную версию.
- Пока событий мало, многие панели пустые — это нормально.

**Ограничения.** Вьюхи читают таблицы `users`, `diary_entries`, `user_premium_state`: если будущая миграция меняет тип или удаляет их колонки `created_at`/`media_type`/`purchased_at`/`plan_kind`/`plan_duration`, Postgres откажется, пока вьюхи не удалены (`DROP VIEW IF EXISTS v_analytics_...`; подробности в шапке миграции `d4a7e1c05b92`). «Экраны, которые не открывали ни разу» в базе не видны (список существующих экранов хранится в `analytics_screens.json`), их по-прежнему показывает отчёт из способа А.

### Способ В. Дашборды в Metabase (если удобнее кликать самому, чем открывать готовый дашборд)

> Этот шаг я не мог проверить у себя (в моём окружении нет Docker), поэтому шаги ниже собраны по документации Metabase. Если что-то не сойдётся, пишите. SQL-запросы из этой инструкции я прогнал на настоящем Postgres, и роль тоже проверял там же.

**1. Создайте read-only роль для Metabase.** Metabase — это полноценный SQL-клиент, поэтому ему нельзя давать логин приложения: под ним видны пользователи и хеши паролей. Роль ниже видит только аналитику. Выполните один раз:

```bash
docker compose exec db psql -U seenly -d seenly -c "
CREATE ROLE metabase_ro LOGIN PASSWORD 'ПРИДУМАЙТЕ-ДЛИННЫЙ-ПАРОЛЬ';
GRANT CONNECT ON DATABASE seenly TO metabase_ro;
GRANT USAGE ON SCHEMA public TO metabase_ro;
GRANT SELECT ON analytics_events, v_analytics_screen_views, v_analytics_daily_active, v_analytics_events_daily,
                v_analytics_registrations_daily, v_analytics_diary_daily, v_analytics_premium_daily, v_analytics_retention TO metabase_ro;"
```

Проверено: под этой ролью читаются аналитические таблицы и вьюхи, а `users`, `rate_limit_hits` и любые записи запрещены.

**2. Запустите Metabase** (он не стартует по умолчанию, только с флагом):

```bash
docker compose --profile analytics up -d metabase
```

Первый запуск занимает минуту-две.

**3. Откройте его.** Порт привязан только к `127.0.0.1`, наружу он не торчит и не должен.
- На своём компьютере: http://localhost:3000
- На сервере: с вашего компьютера `ssh -L 3000:localhost:3000 user@server`, не закрывая окно, откройте http://localhost:3000

**4. Первый вход.** Metabase попросит создать админа (это локальная учётка Metabase, к приложению отношения не имеет). Когда дойдёт до «Add your data»:
- Database type: **PostgreSQL**
- Host: `db`, Port: `5432`, Database name: `seenly`
- Username: `metabase_ro`, Password: тот, что придумали

**5. Первые графики.** «New → SQL query», выберите базу, вставьте запрос, Run, затем «Save». Собрать несколько сохранённых вопросов на один Dashboard — минут десять.

Готовые запросы (`build = 'release'` уберите, пока смотрите свои debug-запуски):

```sql
-- Топ экранов за 30 дней
SELECT screen,
       COUNT(*) FILTER (WHERE nav <> 'back') AS opens,
       COUNT(DISTINCT anon_id)               AS devices,
       ROUND(AVG(seconds_on_screen))         AS avg_seconds
FROM v_analytics_screen_views
WHERE kind = 'screen' AND day >= CURRENT_DATE - 30 AND build = 'release'
GROUP BY screen ORDER BY opens DESC;

-- Открытия одного экрана по дням
SELECT day, COUNT(*) FILTER (WHERE nav <> 'back') AS opens
FROM v_analytics_screen_views
WHERE screen = 'PremiumScreen' AND day >= CURRENT_DATE - 60
GROUP BY day ORDER BY day;

-- Активные устройства по дням
SELECT day, active_devices, signed_in_users, sessions
FROM v_analytics_daily_active WHERE build = 'release' ORDER BY day;

-- Ключевые действия за 30 дней
SELECT name, SUM(events) AS events
FROM v_analytics_events_daily
WHERE day >= CURRENT_DATE - 30 AND build = 'release'
GROUP BY name ORDER BY events DESC;

-- Онбординг: сколько устройств дошло до каждого шага
SELECT (props->>'step')::int AS step, props->>'name' AS name, COUNT(DISTINCT anon_id) AS devices
FROM analytics_events
WHERE name = 'onboarding_step' AND ts >= now() - interval '30 days' AND build = 'release'
GROUP BY 1, 2 ORDER BY 1;
```

Вьюхи (`v_analytics_*`) уже прячут сложную часть (подсчёт «времени на экране»), так что в конструкторе Metabase можно просто выбрать вьюху и группировать по `screen` или `day`.

**Ограничения этой связки:**
- Metabase хранит свои настройки в файле внутри тома `metabase_data`. Для одного-двух человек этого достаточно, но том надо бэкапить, иначе дашборды пропадут вместе с ним. Для команды нужно переводить Metabase на отдельную базу Postgres (документация Metabase: «Configuring the application database»).
- Список «экранов, которые не открыли ни разу» живёт только в отчёте (способ А): список существующих экранов не хранится в БД. Для дашборда его можно вставить в запрос вручную, но это лишний труд.
- В `docker-compose.yml` стоит `image: metabase/metabase:latest`. Перед выкладкой на сервер замените `latest` на конкретную версию, иначе Metabase может обновиться без вашего ведома.

## 3. Как проверить, что всё работает (две минуты)

1. Запустите бэкенд и приложение (debug-сборка, как обычно).
2. В консоли `flutter run` появятся строки `[analytics] screen_view DiaryScreen {...}`: это события, которые ушли в очередь.
3. Походите по нескольким экранам и **сверните приложение** (или подождите 15 секунд). Это запускает отправку.
4. `docker compose exec api python -m scripts.analytics_report` — в разделе «Экраны» должны появиться те, где вы были.

Если пусто:
- В Настройках → «приватность» включена ли «анонимная статистика».
- Приложение действительно ходит на этот сервер (адрес задаётся `--dart-define=SEENLY_API_BASE_URL=...`).
- `ANALYTICS_ENABLED` в `backend/.env` не выставлен в `false`.
- Логи бэкенда: `docker compose logs api | grep analytics`. Ответ `429` значит, что сработал rate limit (20 пачек в минуту с одного устройства), `422` — сломан формат пачки.

## 4. Как добавить своё событие

```dart
import '../analytics/analytics.dart';   // путь зависит от места файла

Analytics.instance.track('wrapped_shared', {'period': 'month'});
```

Правила (сервер их проверяет и лишнее выбрасывает молча):

- **Имя:** `snake_case`, латиница, начинается с буквы, до 64 символов. Глагол в прошедшем времени: `diary_entry_logged`, а не `log_diary`.
- **Свойства:** плоские, значения только строка (до 120 символов), число, `true/false`. Списки и вложенные объекты выбрасываются.
- **Никогда не отправляйте:** названия тайтлов, тексты заметок и отзывов, поисковые запросы, e-mail, имена пользователей, код приглашения. Вместо текста присылайте **форму**: длину (`query_len`), флаг (`has_note`), число результатов. Это обещание, которое мы даём в настройках приложения и в политике конфиденциальности.
- Ставьте `track` **после** успешного действия (после `await`), иначе посчитаете то, что не получилось.
- Лучше в сервисе (`lib/services/*_service.dart`), а не в виджете: тогда событие ловит все места, откуда действие вызывают.

Новый **экран** ничего не требует: он попадёт в аналитику сам, если класс виджета заканчивается на `Screen` (шторка — на `Sheet`). После добавления или переименования экрана перегенерируйте список существующих:

```bash
cd mobile && python3 tools/analytics/list_screens.py          # обновить
python3 tools/analytics/list_screens.py --check                # проверить, что список свежий
```

Иначе в отчёте новый экран попадёт в строку «есть в данных, но нет в списке экранов».

## 5. Что нужно знать о границах

- **`flutter build --obfuscate` сломает имена экранов** (классы переименуются). Если включите обфускацию, придётся давать маршрутам явные имена через `RouteSettings(name: ...)`: наблюдатель их предпочитает.
- **Версия приложения** в отчёте будет `dev`, пока вы не передаёте `--dart-define=SEENLY_APP_VERSION=1.2.3` при релизной сборке (рядом с `SEENLY_API_BASE_URL`).
- **Шторки без своего класса** (собранные прямо в `showModalBottomSheet` из `Container`/`Padding`) попадают в `(unnamed)`. Их не потеряли, но и по имени не различить.
- **Режим «вместе» на Главной:** если человек в нём ушёл на другую вкладку и вернулся, вкладка засчитается как `HomeScreen`, а не `CoViewHubScreen`.
- **Объём:** одна активная сессия — десятки событий. До нескольких миллионов строк Postgres справляется без вопросов; таблица чистится по `ANALYTICS_RETENTION_DAYS` (по умолчанию 400 дней). Если приложение вырастет на порядки, нужна партиционированная таблица или отдельное хранилище: до этого момента далеко.
- **Прод-безопасность:** сейчас в `docker-compose.yml` Postgres опубликован наружу на порт 5432 с паролем `seenly/seenly`. Для разработки нормально, для сервера надо убрать `ports` у `db` и сменить пароль. Это вопрос уже не аналитики, но данные аналитики лежат там же.

## 6. Приватность, удаление, отключение

Что именно собирается и как это описать в политике конфиденциальности: [`privacy_data_inventory.md`](privacy_data_inventory.md).

- **Выключатель у пользователя:** Настройки → «приватность» → «анонимная статистика». Выключение останавливает сбор сразу, очищает неотправленное и стирает id устройства.
- **Удаление аккаунта:** при окончательном удалении (через 30 дней после запроса) стираются все события аккаунта и **всех устройств, с которых он входил**, включая события до входа (онбординг, экран логина).
- **Выключить целиком на сервере:** `ANALYTICS_ENABLED=false` в `backend/.env`. Эндпоинт продолжит отвечать 202 и ничего не сохранит, чтобы установленные приложения не начали ретраи.
